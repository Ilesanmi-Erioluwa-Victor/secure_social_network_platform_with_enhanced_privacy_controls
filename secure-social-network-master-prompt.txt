You are building a full-stack web application called "SecureConnect" —

PROJECT GOAL
-------------
A social platform where users can register, create profiles, post
content, follow/friend other users, and message each other privately —
with strong security (encrypted DMs, MFA, RBAC) and granular privacy
controls (per-post visibility, custom audience lists, blocking).

TECH STACK (use exactly this)
-------------------------------
Frontend:
  - React (Vite)
  - Tailwind CSS (no Bootstrap)
  - React Router
  - Axios for API calls
  - Zustand or Context API for state (no Redux needed)
  - libsodium-wrappers (client-side encryption for DMs)

Backend:
  - Node.js + Express
  - MongoDB Atlas + Mongoose
  - JWT (access + refresh token pattern)
  - bcrypt for password hashing
  - speakeasy + qrcode for TOTP-based MFA
  - helmet, cors, express-rate-limit, express-validator
  - Brevo transactional HTTP API (axios POST) for verification/reset
    emails — NOT SMTP/Nodemailer (Render blocks SMTP ports)
  - Supabase Storage for avatar/media uploads (not local disk, not S3)

Hosting:
  - Backend: Render
  - Frontend: Vercel
  - Database: MongoDB Atlas
  - File storage: Supabase Storage

DATABASE SCHEMA (Mongoose)
-----------------------------
User:
  - name, username (unique), email (unique), passwordHash
  - role: enum ["user", "moderator", "admin"], default "user"
  - mfaEnabled: boolean, mfaSecret: string (encrypted at rest)
  - publicKey: string (for E2E messaging, generated client-side on
    signup, private key never leaves the client)
  - bio, avatarUrl, isVerified, isSuspended
  - blockedUsers: [ObjectId]
  - refreshTokens: [{ token, createdAt, expiresAt }]
  - createdAt, updatedAt

Post:
  - author: ObjectId(User)
  - content, mediaUrls: [string]
  - visibility: enum ["public", "friends", "custom", "only_me"]
  - customAudience: [ObjectId]  (used when visibility === "custom")
  - likes: [ObjectId], commentsCount
  - createdAt, updatedAt

Comment:
  - post: ObjectId(Post), author: ObjectId(User)
  - content, createdAt

FriendRequest / Follow:
  - requester: ObjectId(User), recipient: ObjectId(User)
  - status: enum ["pending", "accepted", "rejected"]

Message (E2E encrypted):
  - sender, recipient: ObjectId(User)
  - ciphertext: string (already encrypted on client before send)
  - nonce: string
  - createdAt, readAt

AuditLog:
  - user: ObjectId(User), action, ipAddress, userAgent, timestamp

Report:
  - reporter: ObjectId(User), targetType (post/comment/user)
  - targetId, reason, status: ["pending","reviewed","dismissed"]

CORE FEATURES TO IMPLEMENT
-----------------------------
1. AUTHENTICATION & MFA
   - Register/login with bcrypt password hashing
   - Email verification link sent via Brevo API
   - JWT access token (15 min) + refresh token (7 days, httpOnly cookie)
   - TOTP-based MFA (speakeasy): user enables MFA, scans QR (qrcode
     package generates it), must enter code to complete login when
     enabled
   - Account lockout after 5 failed login attempts (rate-limited)

2. ROLE-BASED ACCESS CONTROL (RBAC)
   - Roles: user, moderator, admin
   - Middleware `requireRole(["admin"])` guarding admin routes
   - Moderators can review reports and suspend content; only admins
     can manage user roles and view audit logs

3. PRIVACY CONTROLS (the core differentiator of this project)
   - Per-post visibility: public / friends-only / custom list / only me
   - Custom audience picker (multi-select friends)
   - Block list: blocked users cannot view profile, posts, or message
   - Profile-level settings: who can send friend requests, who can see
     friends list, who can see email/phone
   - "Download my data" and "Delete my account" (data portability +
     right to erasure, referenced in the project's privacy justification)

4. END-TO-END ENCRYPTED MESSAGING
   - On signup, client generates a libsodium keypair; private key is
     stored only in the browser (IndexedDB), public key sent to server
   - To send a DM: fetch recipient's public key, encrypt message
     client-side with libsodium box encryption, send only ciphertext +
     nonce to server
   - Server never sees plaintext messages — this is the key security
     claim to demonstrate/screenshot for your defense

5. SOCIAL FEATURES
   - Profile creation/edit, avatar upload (Supabase Storage)
   - Follow/friend request system with accept/reject
   - News feed showing posts from friends + public posts, respecting
     visibility rules server-side (never trust the client to filter)
   - Like/comment on posts
   - Content reporting -> moderator review queue

6. SECURITY HARDENING (for your "simulated attack" testing chapter)
   - helmet for secure headers
   - express-rate-limit on login, register, password reset endpoints
   - express-validator / zod for input validation on every route
   - Mongoose schema-level sanitization (no raw query injection)
   - CORS locked to your Vercel frontend origin only
   - Audit logging of sensitive actions (login, role change, account
     deletion)
   - Passwords never logged or returned in any API response
   - HTTPS enforced (Render/Vercel provide this by default)

7. ADMIN DASHBOARD
   - View reported content queue, suspend/reinstate users
   - View audit logs
   - Basic usage stats (user count, post count, reports pending)

NOTES
========================================================================
- Keep private keys client-side only; this is your strongest security
  claim and easiest to demonstrate in your defense (show the DB
  collection with only ciphertext visible).
- Server-side visibility enforcement (not just hiding things in the
  UI) is what separates "real" privacy controls from cosmetic ones —
  make sure every feed/profile query filters by visibility rules in
  the Mongoose query itself, not after fetching.
- If your supervisor wants a simpler stack, this can be dropped to
  your PHP/PostgreSQL/Supabase/Vanilla JS pattern instead — the schema
  and feature list stay the same, only the backend syntax changes.
